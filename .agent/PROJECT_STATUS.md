### 🔍 New findings from 2026-07-09 live verification (not in the original 2026-07-08 audit)

- **Camera severely cropped — board never fully in frame — ✅ FIXED 2026-07-09.** The physical camera (correctly positioned per `docs/hardware/pinout.md`'s 2"/7"/45° spec) was only ever capturing a dead-centered ~39%×39% crop of the sensor, regardless of physical aiming — not a hardware/positioning problem, and not an inherent ROS/camera_ros limitation. Root cause: `camera_ros`'s `sensor_mode` parameter was never pinned in `perception_launch.py`, so libcamera's own mode-selection heuristic silently picked a windowed raw sensor mode instead of the sensor's native full-FOV 2×2-binned mode — the exact bug our own (unused) Python fallback camera backend already had a fix for, just never applied to the backend actually in production. Fixed with a one-line launch-parameter addition (`sensor_mode: '1640:1232'`); no scripts or workarounds. This one fix also resolved the `board_detector_node`/`piece_detector_node`/camera-intrinsic-calibration items above, all of which had looked like separate "unverified" gaps but shared this single root cause. Full write-up in [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) (Phase 5 section). Commit `1eec875`.
- **No manual corner-calibration UI, and no visibility into automatic detection at all.** `chess_os.py` originally had a manual drag-the-4-corners UI (`board_corners.json` persistence) that was **deliberately removed** during the 2026-07-08 Chess OS consolidation (Step 1, see Initiative 1 below) on the stated reasoning that `board_detector_node`'s automatic detection made it unnecessary. That reasoning's premise (auto-detection works) wasn't actually true at the time — auto-detection had been silently broken by the camera-framing bug above the whole time, so the board was never in frame for the automatic detector either, and there was no manual fallback to fall back on. Separately, and still true even after today's camera fix: **`board_detector_node` already publishes an annotated corner-overlay debug image (`/perception/board_debug`) that chess_ui doesn't display anywhere** — there's currently no way for a user to visually confirm what the automatic detector found, correct or not, let alone override it. The original manual-corner-drag implementation still exists, unmigrated and orphaned, in `src/chess_perception/scripts/fen_visualizer.py` (a separate, undocumented-in-practice standalone Flask app not wired into any current launch file or `setup.py` entry point — `docs/features/vision-system.md`'s one-line description of it is also stale, describing it as the old "FEN web visualizer" rather than its actual corner-calibration feature). Not yet scoped as a phase — see [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) for discussion.

### 🐛 Known Bug — `camera_ros` stops serving new subscribers after ~2h uptime

Discovered twice in one session (2026-07-08), both times independently: after `camera_node` (the `camera_ros` package, not our own `chess_perception/camera_node.py` fallback) runs for roughly 1.5-2+ hours, **new** subscribers to `/camera/image_raw/compressed` — including `ros2 topic hz` itself, and a freshly-started `chess_ui`/`chess_os` — receive **zero** frames, while subscribers that connected earlier (`board_detector_node`, `piece_detector_node`) keep receiving frames fine. DDS pub/sub matching looks correct (`ros2 topic info --verbose` shows the subscriber registered); the publisher just doesn't send anything to it. Restarting `camera_node` (or the whole perception stack) immediately fixes it — a fresh instance serves new subscribers at a full 30Hz. Not yet root-caused (likely an image_transport lazy-publish/subscriber-count edge case inside `camera_ros` itself, not our code). **If the Chess OS raw camera view or a freshly-launched perception node ever shows no camera data, try restarting `camera_node` before assuming something else broke.**

## 🧠 Strategic Initiatives

### 1. Chess OS / `code/` Architecture Consolidation — ✅ COMPLETE (2026-07-08)

**Problem**: `chess_os.py` grew from "a UI" into a monolith that reimplements vision detection, gantry coordinate math, and calibration/homing logic that already exists correctly inside the ROS packages. It isn't installable as a ROS package and isn't launched by `full_system_launch.py`.

**Direction**: convert Chess OS into a proper ROS package (e.g. `chess_ui`) — installable via colcon, launchable alongside everything else — and strip it down to a thin UI/API layer that only ever reads from ROS topics/services/actions, never recomputes its own vision or coordinates.

**Plan**: do this one concern at a time, verifying on the Pi after each step, not as one big rewrite:
1. Delete the duplicated vision pipeline (`_detect_pieces`, `_fen_from_detection`, `_opencv_camera_loop`) — display frames/FEN from `chess_perception` topics only.
2. Delete the duplicated `square_to_mm()` — resolve squares via the `MoveGantry` action instead.
3. Replace `_TestRunner` subprocess orchestration with a ROS-native service/action in `chess_hw_interface`.
4. Split the file into modules (`app.py`, `ros_client.py`, `templates/`, `state.py`) and move it into a real `src/chess_ui/` package with `package.xml`/`setup.py`.
5. Once each `code/` standalone script's ROS equivalent is confirmed superseding it, delete the script (see the Architecturally Broken list above).
